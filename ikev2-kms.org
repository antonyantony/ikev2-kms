#+begin_abstract
This document specifies a method for deriving and distributing IPsec
Encapsulating Security Payload (ESP) keys within large groups using an
extended Internet Key Exchange Protocol Version 2 (IKEv2).  A Group Key
Management Server (GKMS) acts as a trusted authority that
authenticates nodes and coordinates key derivation.  The GKMS holds a
group key that is distributed to all current group members and also
proxies messages between pairs of nodes to derive unique pairwise
session keys via a Diffie-Hellman (DH) exchange.  The final ESP key
for each pair is derived by combining the group key and the pairwise
key using an XOR operation; only the two communicating nodes possess
both inputs, so only they can derive the ESP key.  This approach
reduces the number of IKEv2 control-plane states on each node to O(1)
relative to group size, supports dynamic group membership, and allows
the GKMS to centrally manage certain control-plane operations such as
Security Association (SA) deletion and rekeying.
#+end_abstract

#+RFC_KEYWORDS: ("IPsec" "ESP" "IKEv2")

* Introduction

Modern distributed environments that operate under a single
administrative domain -- for example, AI or machine learning (ML)
compute clusters -- often comprise a large number of worker nodes that
exchange sensitive data over IP networks.  To protect the
confidentiality and integrity of these communications, IPsec ESP
[[RFC4303]] can be employed.

In the architecture described in this document, a single trusted
server called the Group Key Management Server (GKMS) authenticates
each node and coordinates cryptographic key derivation.  Each node
enrolls with the GKMS and receives credentials that authorize its
participation in the group.

Each pair of communicating nodes independently derives a unique
pairwise encryption key.  This is achieved through a DH exchange
[[RFC7296]] that is proxied by the GKMS, so nodes do not need a direct
IKEv2 channel with each other.  The final ESP session key is computed
as the XOR of two components: (1) the long-lived pairwise key derived
from the DH exchange and (2) the group key distributed by the GKMS.
Because each node in a pair independently contributes to the DH
exchange, the GKMS cannot act as a man in the middle.

An IPsec peer MAY delegate certain IKEv2 control-plane functions to
the GKMS.  For example, deletion of an ESP Security Association (SA)
from all relevant group members can be coordinated by the GKMS on
behalf of a node, avoiding the need for that node to send individual
Delete messages [[RFC7296]] to each peer.  The GKMS also coordinates
rekeying when group membership changes.

** Comparison with Shared Group Keys

As an optional operational mode, a deployment MAY choose to relax the
requirement for unique pairwise keys and permit all group members to
share a single ESP encryption key.  This is achieved by setting the
pairwise key component to zero, so that the final ESP key equals the
group key distributed by the GKMS.  A mixed mode, where some node pairs
use unique pairwise keys while others use the group key, is also
possible but is NOT the preferred mode and is described only for
completeness.  See [[I-D.xia-ipsecme-eesp-stateless-encryption]] for a
discussion of the related security and operational trade-offs.

** Limitations of Full-Mesh IKE Keying

If every node were to establish a direct IKEv2 SA with every other
node, each participant would need to maintain N−1 control-plane SAs,
along with all associated state such as certificates, nonces, and
traffic selectors.  This full-mesh approach does not scale to large
deployments: the number of SAs grows quadratically with group size, and
the operational overhead of managing individual IKE exchanges,
including retransmissions and SA deletion, becomes prohibitive.  The
method defined in this document avoids this quadratic growth by
introducing the GKMS as a central coordinator.

Similar scalability challenges and design goals appear in other
published systems, including Google PSP [[PSP]], Google Falcon
[[Falcon]], the Ultra Ethernet Consortium's specification [[UEC-TSS]],
and the IETF EESP work [[I-D.ietf-ipsecme-eesp]].  MLS [[RFC9420]] and
Double Ratchet mechanisms were considered as potential foundations,
but were not chosen because they require frequent key-update round
trips and continuous state evolution even in the absence of
membership changes.

* Terminology

This document uses the following terms from [[RFC4301]]: Encapsulating
Security Payload (ESP), Security Association (SA), Security Policy
Database (SPD), and IPsec Processing (IPsec processing entry/exit).

The following terms are specific to this document:

Group Key Management Server (GKMS)::
  A trusted server that authenticates group members, distributes a
  group key, and facilitates pairwise key derivation between members.
  The GKMS may be deployed with one or more redundant instances that
  share the same cryptographic state.

Group Key::
  A random key generated by the GKMS and distributed to all current
  members of a group.  The group key is re-generated and re-distributed
  whenever membership changes.

Pairwise Key::
  A long-lived symmetric key derived exclusively by a pair of
  communicating nodes through a DH exchange that is proxied by the
  GKMS.  The GKMS does not learn the pairwise key.

Composite ESP Key::
  The key material used for ESP encryption and decryption.  It is
  computed as the XOR of the Group Key and the Pairwise Key.

* Overview of the Protocol

** Architecture

The system consists of three logical components:

1. The Group Key Management Server (GKMS).
2. Enrolled group members (called "nodes" in this document).
3. An IP network that carries both data traffic (ESP) and the IKEv2
   control messages that are proxied through the GKMS.

Nodes authenticate to the GKMS during enrollment and obtain any
necessary credentials.  The GKMS distributes the current Group Key to
each enrolled node.  When two nodes wish to establish an ESP SA, they
perform a DH exchange [[RFC7296]] with each other's messages relayed
by the GKMS.  Each node independently computes the same Pairwise Key
from the DH output.  Finally, each node computes the Composite ESP
Key as:

: Composite ESP Key = Group Key XOR Pairwise Key

The GKMS does not participate in the DH computation and therefore
cannot derive either the Pairwise Key or the Composite ESP Key.

** Key Derivation Exchange

When node Alice wishes to communicate securely with node Bob, the
following steps occur:

1. Alice sends a GKMS_KeyRequest message to the GKMS identifying Bob.
2. The GKMS proxies the request to Bob.
3. Bob responds with a GKMS_KeyResponse message relayed back to Alice.
4. Alice and Bob perform a standard IKEv2 Diffie-Hellman Key Exchange
   [[RFC7296]] using the messages relayed in steps 2 and 3.  The KE
   payload is conveyed in the IKE_AUTH request and response.
5. Both Alice and Bob derive the Pairwise Key from the DH shared secret
   using a suitable Key Derivation Function (KDF) [[RFC9370]].
6. Both Alice and Bob independently compute:

   Composite ESP Key = Group Key XOR Pairwise Key

A portion of the DH output MUST be used in the derivation of the
Pairwise Key such that the GKMS cannot compute the Pairwise Key from
the relayed KE payloads alone.  Specifically, the DH shared secret
S MUST be an input to the KDF that produces the Pairwise Key; the GKMS
never sees S.

** Adding a New Member

When a new member joins the group, the GKMS authenticates the node,
distributes the current Group Key, and communicates the group security
policy.  The policy includes at minimum: the supported ESP crypto
suites, the ordered list of DH groups (where the first element is the
preferred group for initiating the DH exchange), and any traffic
selectors.  The new member is then able to derive pairwise keys with
existing members as described in the key derivation exchange above.

** Removing a Member <<removing-a-member>>

When the GKMS removes one or more members, it generates a new Group
Key and distributes it to all remaining members.  Upon receiving the
new Group Key, each remaining node MUST promptly re-derive all
Composite ESP Keys using the new Group Key and the existing Pairwise
Keys.  The removed members cannot derive the new keys because they do
not possess the new Group Key.

The previous Group Key MAY remain valid for a short transition period
to allow for clock skew or delivery delays.  A node that has not yet
received the new Group Key continues to use the previous Composite
ESP Key; this window SHOULD be kept short to limit the rekey latency.

[NOTE: An atomic rekey mechanism may be desirable to prevent race
conditions during membership changes.  In such a scheme, the GKMS would
first distribute the new Group Key to all (or most) members and then
send an atomic "activation" message indicating the time or event at
which the new key becomes active.  This prevents one node from
transmitting with the new key while its peer is still using the
previous key.  The design of this mechanism requires further
evaluation.]

** Time-Based Rekeying

At predefined intervals, the GKMS generates a new Group Key and
distributes it to all active nodes.  Each node re-derives its
Composite ESP Keys as described above.  This provides forward secrecy
over time and limits the cryptoperiod of any given key without
disrupting established SAs.

** Packet-Based Rekeying

In the packet-based rekey model, the GKMS does not maintain packet or
byte counters per SA.  Instead, when a node detects that an SA has
reached a local usage threshold, it notifies the GKMS, which then
initiates a time-based rekey cycle.  This model adapts rekey frequency
to actual traffic volume.

** Delegated SA Deletion <<delegated-sa-deletion>>

An IKEv2 node that wishes to terminate an SA is normally required to
send a DeleteNotify payload [[RFC7296]] to each peer, await a
response, and retransmit if necessary.  In a large group, performing
this individually for each peer is expensive.

A node MAY instead delegate SA deletion to the GKMS.  In this mode,
the node sends the GKMS a list of peers and their SPIs for which
deletion is requested.  The GKMS then coordinates the deletion
exchange with each affected peer on behalf of the requesting node.

[NOTE: The delegation protocol details, including message formats
and error handling, are to be defined in a future revision of this
document.]

** GKMS Redundancy

A deployment MAY operate multiple GKMS instances in parallel for
availability and load distribution.  All GKMS instances in a domain
MUST share the same cryptographic state, specifically the current Group
Key and any pending rekey state, so that any instance can continue
keying operations without interruption.  A node that discovers a GKMS
instance unreachable SHOULD attempt to contact another instance.

** Using Only the Group Key for ESP

For deployments that do not require pairwise key separation, the
Pairwise Key component MAY be set to a constant zero value.  In this
mode, the Composite ESP Key equals the Group Key, and all group
members share the same ESP encryption key.  This simplifies
implementation but means that compromise of any single node exposes
the group key used for all pairs.  Nodes that require pairwise key
separation SHOULD NOT use this mode.

* Protocol Exchange Details

** Message Scalability

Each pairwise key derivation requires one Round-Trip Time (RTT) between
the two nodes, plus the forwarding latency through the GKMS.  The IKEv2
and ESP cryptographic parameters are selected by the GKMS and conveyed
to both nodes, so no negotiation round trips are needed.

In IPv6 environments, the GKMS MAY use multicast to distribute group
messages -- such as new or updated Group Keys -- to all nodes
simultaneously.  Each node MUST acknowledge receipt of multicast
messages via unicast to the GKMS.

** Traffic Selectors with Multiple Network Interfaces

Hosts with multiple Network Interface Cards (NICs) and IP addresses
require a separate pair of Traffic Selectors (TSi/TSr) for each
IPsec endpoint.  In standard IKEv2, adding a new interface with
MOBIKE [[RFC4555]] or IKE SA Cloning [[RFC7791]] requires three or
more additional IKEv2 exchanges per new endpoint.

In the GKMS model described in this document, no new IKE SA is
established for each additional interface; instead, the GKMS
coordinates the addition of new Traffic Selectors for the existing
IKE SA.  The GKMS has a holistic view of all interfaces on a node and
acts as a proxy to negotiate these additional endpoints.

* Security Considerations

The security of this protocol relies on the following assumptions:

The GKMS is trusted to correctly authenticate members, distribute
Group Keys, and relay DH messages without modification or disclosure.
Compromise of the GKMS allows the attacker to participate in group
communication and to observe the Group Key but does not immediately
reveal Pairwise Keys, because the DH exchange between nodes remains
unobservable to the GKMS.  This property limits the blast radius of
a GKMS compromise compared to schemes in which the key server holds
all pairwise keys (such as G-IKEv2 [[I-D.ietf-ipsecme-g-ikev2]]).

Nodes MUST verify that their DH peer is a legitimate group member by
validating the certificate or credential issued by the GKMS during
enrollment.  Without this verification, a compromised GKMS could
impersonate any member to any other.

Forward secrecy is provided with respect to the Group Key through
time-based and membership-change-based rekeying.  Forward secrecy
with respect to Pairwise Keys is achieved only when both sides perform
a fresh DH exchange; the protocol does not provide Continuous Key
Derivation (CKR) or Double Ratchet-style update mechanisms.

The group-key-only mode (Pairwise Key set to zero) does not provide
pairwise key separation and therefore does not limit the impact of a
node compromise to a single pairwise relationship.

The delegated SA deletion mechanism requires the GKMS to possess
sufficient credentials to authenticate to the removed peer.  The
security implications of this credential sharing require further
analysis and are noted as an open issue.

* Privacy Considerations

The GKMS learns the identities of all communicating pairs because it
relays the key derivation requests.  A privacy-sensitive deployment
SHOULD use opaque or group-pseudonymous identifiers in GKMS requests
to limit identity disclosure to the GKMS.  The DH exchange itself is
authenticated (via credentials issued by the GKMS), so passive
observers of the relayed KE payloads cannot identify the peers without
also compromising the GKMS credential store.

Nodes that use only the Group Key mode reveal their group membership
to any observer of their ESP traffic, because all group members share
the same ESP key.

* Open Issues

This section records known open issues that require resolution in a
future revision of this document.

1. *Delegated SA deletion*: The protocol details for delegating SA
   deletion to the GKMS (message formats, retransmission behavior,
   error handling) are not yet specified.

2. *Atomic rekey*: The design of an atomic rekey mechanism to prevent
   race conditions during group membership changes is open.

3. *GKMS credential for delegated deletion*: The security implications
   of granting the GKMS credentials to send DeleteNotify messages on
   behalf of a node need further analysis.

4. *IANA registration*: All IANA registration requests are pending
   specification of the protocol message formats in a future revision.
